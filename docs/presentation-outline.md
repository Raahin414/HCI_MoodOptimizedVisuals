# MoodSpace: 6–8 minute presentation

This is a demo script, not a claim that a human experiment has finished. Use a clearly marked demo session. Never display automated-test records as real findings.

| Time | Demonstration | What to say |
| --- | --- | --- |
| 0:00–0:45 | Welcome and study consent | Students organize the same work differently. We are testing whether structure, self-reported mood and preference relate; the app does not diagnose emotion. Participation and optional text are separate decisions. Institutional permission remains required before recruitment. |
| 0:45–1:25 | Mood check-in | Select one of three classes or the unclassified option; show pleasantness and energy. Skip text or show explicit save opt-in. Explain that a keyword demonstration is a rule, not a trained model. |
| 1:25–2:35 | All eight gallery previews | Contrast spotlight, status board, calendar, progress drill-down, course groups, priority quadrants, guided intent and editorial briefing. All expose the same five courses, 24 tasks and eight milestones. Select an initial favorite. |
| 2:35–3:35 | Practice and assigned study | Show that the server assigns four UIs independently of the favorite. Start a scored task, inspect a deadline and submit. Point out timer, give-up and stop controls. Explain that the complete protocol has two scored tasks per UI, eight total, and a fresh sandbox each time. Do not complete eight tasks live if it obscures the explanation; use an already completed **demo** run. |
| 3:35–4:10 | Feedback and end check | Show the four short ratings, optional comments, final free choice and end mood check. A final choice can refer to an untested preview and is labeled accordingly. |
| 4:10–5:15 | Research dashboard and export | Sign in using a local server-side secret. Show actual real-participant count and the 3 × 8 coverage matrix. With no real data, read the honest empty state. Show export manifest, canonical events and provenance filtering; do not turn demonstration data into evidence. |
| 5:15–6:10 | Recommendation | With zero support, show `insufficient_evidence` and the participant-choice fallback. Explain eight distinct participants in every compared mood/UI cell, participant-level aggregation, success-first ranking and family-adjusted time. Try another layout to show that the person stays in control. |
| 6:10–7:00 | Research claims and next steps | H1 and H2 require real data; an overall winner is valid. H3 requires a frozen, held-out/prospective adaptation-versus-static comparison. Describe a 6–8 person rehearsal and a possible 72-person exploratory target, not an achieved sample or power guarantee. |
| 7:00–8:00 | Questions / evidence appendix | Present the test report and actual screenshots from the running app if captured. Distinguish browser automation duration from human usability timing. Explain limitations without implying unperformed tests. |

## Suggested slides

1. Question and original academic domain.
2. Eight structures, one data/action contract.
3. Four-layout subset protocol and natural mood reports.
4. Data integrity: consent, canonical IDs, sandbox reset, provenance, withdrawal.
5. Evidence-gated recommendation and zero-data state.
6. Verified software checks and remaining human validation.

## Before presenting

Run the documented automated checks and use their real output. Start both API and frontend. Keep administrator credentials out of screenshots. Save any screenshot to the documented output location; do not fabricate a coverage heatmap. If there are genuine observations, state their consented real count, protocol version, exclusions and missing cells. If there are none, say so plainly. Rehearse the talk with a stopwatch; the table above is only a plan.
